## 00:00-00:35 开场与项目定位

> 大家好，我是零号工位的独立开发者。这个项目叫 AgentLoom。
>
> Agent 会写代码，也会调用各种 Skill。但到了真实研发环境，我们还得知道：
> Skill 从哪里来，谁有权使用，它改了什么，结果又是否可信。
>
> AgentLoom 做的，就是给多 Agent 协作补上一套授权、验证、审批和回放机制。

## 00:35-01:15 为什么使用 AgentTeams

> [稍慢] 这里的协同运行时是 AgentTeams。
>
> 任务进来以后，Manager 先拆解；Investigator 调查根因；Implementer 只在授权
> 范围内修改代码；Verifier 再独立验收。
>
> 这样分工不是为了凑 Agent 数量，而是为了分开相互冲突的责任。写补丁的人不能
> 自己宣布通过；每个角色都要留下证据，最后由 Manager 汇总结论。

## 02:05-03:15 治理链路与 TUI

> 接下来是 AgentLoom 最核心的部分。
>
> 这里回放的是 Task 24 已经固化的 MiniMax Evidence，记录了 severity
> normalization 案例的真实协作与验证结果。现在看到的是脱敏摘要，不会再次请求
> 模型，也不会消耗 Token。
>
> 当 Verifier 要运行测试时，请求会先经过 Higress 确认身份，再由 Policy Broker
> 检查一次性授权。授权绑定了 Agent、Skill、工具、参数和工作区。条件全部匹配，
> 测试才会进入禁网、只读挂载的 Docker 沙箱。
>
> 最终数据库里只有一个成功的 ToolCall。换一个调用者、偷偷修改参数，或者重放
> 已经使用过的授权，都会被拒绝。
>
> 这个 TUI 是 AgentLoom 的治理界面。AgentTeams 负责角色协作；AgentLoom 把任务
> 状态、失败记录、审批和验证结果整理成可检查、可回放的证据。

## 03:15-03:55 原创建设与 Skill 治理

> AgentLoom 的原创重点，是这一层 Skill 治理能力。
>
> 第三方 Skill 进入系统后，会先绑定来源、许可证、版本和内容哈希，再经过分层
> 检测。执行前，Policy Broker 还会把调用者、工具、路径和参数写进一次性授权。
>
> 验证失败、权限越界或证据不完整时，系统会拒绝执行。这样，Skill 就从一个提示词
> 文件，变成有来源、有边界、有验证结果的工程能力。

## 03:55-04:35 人工审批与工程质量

> 对联网、安装依赖或者创建 PR 这类高风险操作，Agent 不能自己批准自己。

## 04:35-05:00 总结与边界

> 最后总结一下。AgentLoom 把任务拆解、根因调查、受控修改和独立验证，连接到
> 人工审批、失败回滚与 Evidence 沉淀。
>
> 它关注的不只是模型能不能写出补丁，更关注谁在什么权限下，用哪一版 Skill
> 做了什么，以及结果如何被证明。
